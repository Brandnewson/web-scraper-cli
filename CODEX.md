# CODEX.md — Behaviour and identity instructions

## Who you are working for

You are working for a final-year Computer Science student at a UK university completing
an individual coursework assignment. The student has strong IR theory knowledge and
wants production-quality, well-reasoned code — not skeleton stubs. They are using a
test-driven development (TDD) workflow: failing tests are written first, then
implementation is iterated until tests pass, then code is reviewed and committed.

## How you must behave

### Code style
- Python 3.11+. Type hints on every function signature, including return types.
- PEP 8 throughout. Line length 88 (Black default).
- Docstrings on every public function and class using Google style.
- No magic numbers — extract all tunable parameters (k1, b, field weights, skip step,
  max edit distance) as named constants or dataclass fields at the top of each module.
- Prefer `@dataclass` over plain dicts for structured data (PageData, Posting, etc).

### TDD discipline
- When asked to implement a feature, first write the test(s) in the appropriate test
  file as a separate step, then implement the feature, then confirm tests pass.
- Tests must use `pytest`. HTTP calls must be mocked with `unittest.mock.patch` or
  `pytest-mock` — the test suite must never make live network requests.
- Aim for >85% line coverage measurable via `pytest-cov`.
- Do not move to the next implementation phase until:
  - all planned tests for the current phase are written,
  - those tests fail first for the expected reason,
  - production-complete behaviour (not stubs/placeholders) is implemented,
  - all current-phase tests pass,
  - and tests are mapped to the phase objective.
- Never ship stub-only implementations. If a unit is implemented in a phase, it must
  satisfy that phase's acceptance objective.

### Environment policy
- Use `conda` for environment management.
- Keep `requirements.txt` as the dependency source of truth for this coursework.
- Do not switch to `uv` in this repo.

### Commit discipline
- One logical change per commit. Do not bundle unrelated changes.
- Commit message format: `type(scope): description`
  - Types: `feat`, `fix`, `test`, `refactor`, `docs`, `chore`
  - Examples: `feat(indexer): add per-field position storage`
              `test(search): add skip pointer boundary cases`
              `fix(crawler): enforce politeness window on failed requests`

### Error handling
- All network calls are wrapped in try/except covering `requests.RequestException`.
- The politeness sleep fires unconditionally before every request — including after
  errors, redirects, and non-200 responses. It is not conditional on success.
- `load` detects a missing or corrupted index file and prints a clear human-readable
  error rather than raising an unhandled exception.
- `find` with an empty argument list prints a usage hint. `print` on an unknown word
  prints an informative message. Neither crashes.

### What to avoid
- Do not use external NLP libraries (NLTK, spaCy, etc). Tokenisation is pure Python.
- Do not use pickle. Serialisation is JSON only.
- Do not import anything not in `requirements.txt`. If a new dependency is needed,
  flag it explicitly before adding it.
- Do not add features not described in CONTEXT.md without flagging them first.
